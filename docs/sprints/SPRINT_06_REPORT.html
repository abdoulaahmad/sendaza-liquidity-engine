Sendaza Liquidity Engine

Sprint 6: Purchase Reservation and Settlement

How an accepted quote becomes safely allocated crypto backing

Implementation complete on 2 September 2026; Railway release gate pending

Honest status: The schema, domain service, API, worker, atomic repository, unit tests, integration scenario, and canonical documentation are implemented. Lint, TypeScript, and 233 unit tests pass. The real PostgreSQL rerun and production migration are not yet complete because the Railway Postgres service currently has no public TCP proxy.

1. Goal

Consume one unexpired purchase quote after Sendaza locks the exact fiat debit, reserve the quote's crypto amount on its configured asset-network, and safely converge with Sendaza's ledger result. SLE does not hold customer fiat and never writes Sendaza balances.

2. Connection to Earlier Sprints

Sprint 4 created immutable quotes containing exact debit, credit, spread, fee, precision, expiry, and backing asset-network evidence. Sprint 5 created fresh, independently matched treasury inventory for each asset-network. Sprint 6 joins those results: a valid quote tells SLE what to reserve, and fresh inventory proves the reservation can be backed.

3. What Was Built

Domain: packages/domain/src/purchase.ts defines the purchase states, stable failures, service boundary, response view, and leased timeout batch.

Database: prisma-purchase.repository.ts serializes competing reservations with row locks and commits purchase, reservation, inventory, transition, timeout job, and outbox event together. The forward migration adds purchase history, immutable settlement evidence, timeout jobs, and separately tracked allocated inventory.

API: POST /purchases, POST /purchases/:id/settlement, and GET /purchases/:id expose a strict Sendaza-only contract. Clients cannot select wallets, providers, networks, policies, amounts, or fees.

Worker: the purchase timeout worker leases bounded batches. A missing acknowledgement moves a reservation to reconciliation and keeps its inventory held.

4. End-to-End Example

Suppose a configured quote says the customer pays 200000.00 fiat and receives 6250000.000000 units of a configured token on one network. Sendaza first locks exactly 200000.00 in its own ledger, then sends the quote ID and its lock reference to SLE.

          reserved -> allocated    inventory released      inventory held

Two concurrent purchases cannot spend the same capacity because PostgreSQL locks the inventory row. A successful settlement converts reserved units into allocated units; they remain unavailable because they now back a customer liability.

5. Fit in the Complete System

Sendaza remains responsible for authentication, KYC, customer authorization, fiat locks, double-entry journals, balances, and the customer interface. SLE remains responsible for quote economics and treasury backing. Fireblocks MPC is not called during a purchase because no blockchain transfer occurs; custody is relevant later when an external withdrawal moves allocated crypto on-chain.

6. Rules Protected

  • All amounts are atomic-unit bigint values internally and decimal strings at the API.
  • A quote is consumed once and a financial mutation is idempotency protected.
  • Inventory is scoped by asset-network; the same token on two networks is not interchangeable.
  • Reservation cannot make sellable inventory negative.
  • State changes and their outbound event share one PostgreSQL transaction.
  • Timeout is uncertainty, not proof of failure, so inventory stays held.
  • Completed and rolled-back history is immutable.
  • No private key, seed phrase, or customer ledger mutation enters SLE.

7. Test and Environment Evidence

Passed: ESLint; strict TypeScript compilation; API and worker production builds; 42 unit suites with 233 tests, including purchase calculations and states, parser rejection, API mappings, and treasury refresh preservation.

Implemented but awaiting rerun: a real PostgreSQL test races two purchases against limited inventory, verifies only one succeeds, commits one reservation, rolls another back, times another out, and checks held inventory plus lifecycle outbox events.

Environment limitation: the Railway Postgres service exposes only its private hostname and currently has no public TCP proxy. The local test runner therefore cannot reach sle_test. This is an infrastructure access gate, not a passing database result.

8. Limitations and Next Dependency

The generic HTTP idempotency record and the purchase transaction still commit separately. Database uniqueness prevents duplicate allocation, but a crash after purchase commit and before response persistence can leave an idempotency key in progress. Automated recovery is required before real-funds launch.

Sprint 6 closes only after the isolated PostgreSQL scenario passes, migration 11 is verified in production, and the report is regenerated with that evidence. Sprint 7 then builds cached network-fee snapshots for external withdrawals; it does not change purchase pricing or reservation behavior.

9. Glossary

Reservation: crypto inventory temporarily held for one purchase. Allocation: treasury holdings committed as backing for a customer crypto liability. Asset-network: one asset on one blockchain, such as USDT on Ethereum versus USDT on Tron. Row lock: a database rule that makes competing updates wait their turn. Outbox: events stored with the financial change and delivered later. Reconciliation: investigation of an outcome that cannot be safely classified. Compensating record: a new linked correction instead of rewriting history.
